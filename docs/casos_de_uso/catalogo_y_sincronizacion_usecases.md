| **NOMBRE** | C01 — Sincronizar catálogo completo (snapshot) |
| --- | --- |
| **Actor principal** | Tiempo/Arranque o Servicio de Catedra (aviso Kafka) |
| **Actor secundario** | Servicio de la cátedra |
| **Descripción** | Obtiene de la cátedra el snapshot completo del catálogo y reemplaza de forma consistente la copia local de categorías, profesionales y horarios semanales, registrando como versión local exactamente la `snapshotVersion` recibida. |
| **Alcance** | Servicio de catálogo y sincronización |
| **Precondición** | - JWT técnico vigente y configuración de integración disponible.<br>- Se cumple al menos una de estas condiciones: (a) la base local está vacía y no tiene versión aplicada; (b) la versión local es menor que `oldestAvailableVersion` de la cátedra; (c) se detecta una discontinuidad o un estado local que no puede verificarse al sincronizar incrementalmente o al verificar la version del catalogo. |
| **Flujo** | **1-** El servicio de catálogo detecta que debe reconstruir la copia local.<br>**2-** Solicita el snapshot al servicio cátedra (`GET /api/synchronization/snapshot`) con el JWT técnico.<br>**3-** El servicio cátedra responde `200` con `snapshotVersion`, `generatedAt` y las tres colecciones (categorías, profesionales y horarios semanales), habilitados y deshabilitados.<br>**4-** El servicio valida que la respuesta esté completa y sea consistente entre sí (colecciones presentes y referencias entre entidades resueltas).<br>**5-** En una única unidad de trabajo, reemplaza las tres colecciones locales por las del snapshot y registra `snapshotVersion` como versión local, si las tres colecciones quedaron aplicadas.<br>**6-** Confirma la unidad de trabajo y registra el resultado de la sincronización (versión aplicada, fecha y resultado y tipo de sincronización: `FULL`) para poder informarlo. |
| **Flujo alternativo** | **1.1, Ya hay una sincronización en curso:** no se inicia otra en paralelo y se descarta esta solicitud (termina).<br>**2.1, La cátedra responde `401` (JWT vencido o rechazado):** se ejecuta la autenticacion de cuenta tecnica (X01) para renovarlo y se retoma en el paso 2, una sola vez.<br>**2.2, Timeout, corte de conexión, `503` o `500`:** se reintenta con espera creciente y un máximo de intentos. Si se agotan, se registra el error, se conserva la copia local previa y termina; se reintentará en la próxima verificación periodica o en el próximo arranque.<br>**2.3, La cátedra responde `403` (el JWT no tiene el rol de cliente técnico):** no se reintenta, se registra el error de integración y termina.<br>**4.1, La respuesta está incompleta o es inconsistente:** se descarta, se registra el error, no se modifica la copia local y termina.<br>**5.1, Falla la persistencia:** se revierte toda la unidad de trabajo, la copia y la versión anteriores quedan intactas, se registra el error y termina. |
| **Postcondición** | **- Éxito:** la copia local contiene exactamente las entidades del snapshot y la versión local es `snapshotVersion`. Si la cátedra ya publicó versiones posteriores, las aplica una sincronización incremental posterior (La verificacion periodica del catalogo (C03) la repite una vez tras la sincronizacion completa (C01), y también pueden aplicarlas la sincronizacion incremental (C02) o la verificacion periodica (C03) más adelante).<br>**- Fracaso:** la copia local y la versión anteriores no cambian (nunca queda un estado parcial) y el error queda registrado. |

| **NOMBRE** | C02 — Sincronizar catálogo incrementalmente |
| --- | --- |
| **Actor principal** | Servicio de la cátedra (iniciador: aviso `CatalogUpdated` por Kafka) |
| **Actor secundario** | Servicio de la cátedra (en rol de soporte: metadata, cambios y entidades en Redis) |
| **Descripción** | Ante un aviso de nueva versión del catálogo, consulta en Redis la metadata y los cambios posteriores a la versión local, y los aplica en orden a la copia local (categorías, profesionales y horarios semanales). La versión local avanza únicamente cuando los cambios de esa versión quedaron aplicados. Si no puede continuar de forma incremental, delega en sincronizacion completa (C01). |
| **Alcance** | Servicio de catálogo y sincronización |
| **Precondición** | - Auntenticacion de cuenta tecnica y obtencion de configuracion completado (topic `catedra.catalog.{groupId}`, consumer group y credenciales de Redis disponibles).<br>- El servicio está consumiendo el topic del catálogo. |
| **Flujo** | **1-** El servicio recibe un mensaje `CatalogUpdated` (`eventId`, `newVersion`, `occurredAt`, `source`, `schemaVersion`) del topic del catálogo.<br>**2-** Valida el mensaje (campos requeridos presentes y `schemaVersion` igual a 1; ignora campos desconocidos).<br>**3-** Verifica que el `eventId` no haya sido procesado antes.<br>**4-** Lee en Redis la metadata del catálogo (`currentVersion` y `oldestAvailableVersion`).<br>**5-** Determina las versiones pendientes (desde la versión local + 1 hasta `currentVersion`) y verifica que se pueda continuar de forma incremental (la versión local no es menor que `oldestAvailableVersion`).<br>**6-** Toma la primera versión pendiente `v`, lee `catedra:sync:changes:{v}` (IDs afectados por colección) y el estado vigente de cada ID en los Hashes correspondientes de Redis.<br>**7-** En una única unidad de trabajo, aplica esos cambios a la copia local y avanza la versión local a `v`.<br>**8-** Si quedan versiones pendientes, repite los pasos 6 y 7 con la siguiente, siempre en orden ascendente.<br>**9-** Registra el `eventId` como procesado y el resultado de la sincronización (versión aplicada, fecha, resultado y tipo de sincronización: `INCREMENTAL`), y confirma el offset del mensaje en Kafka. |
| **Flujo alternativo** | **1.1, Ya hay otra sincronización en curso (C01, C02 o C03):** se espera a que termine y se retoma en el paso 4, porque la versión local pudo cambiar. No se procesan dos sincronizaciones en paralelo.<br>**2.1, El mensaje es inválido (JSON no interpretable, campos requeridos ausentes o `schemaVersion` desconocida):** se descarta, se registra el error y se confirma el offset (termina). Un aviso perdido lo recupera la verificacion periodica de la version del catalogo(C03).<br>**3.1, El `eventId` ya fue procesado:** no se repite ningún efecto, se confirma el offset y termina.<br>**4.1, Redis no está disponible (timeout o corte de conexión):** se reintenta con espera creciente y un máximo de intentos. Si se agotan, se registra el error, no se avanza la versión local, se da el aviso por atendido (se confirma el offset) y termina; el atraso lo recupera laverificacion periodica de la version del catalogo(C03).<br>**4.2, Redis rechaza las credenciales:** se ejecuta la autenticacion de la cuenta tecnica para obtener la configuración vigente y se retoma en el paso 4, una sola vez. Si persiste, se registra el error y termina como en 4.1.<br>**5.1, La versión local ya alcanzó `currentVersion`:** no hay nada que aplicar; se registra el `eventId`, se confirma el offset y termina.<br>**5.2, No hay versión local, es menor que `oldestAvailableVersion` o es mayor que `currentVersion` (discontinuidad o estado no verificable):** se ejecuta C01. Si termina con éxito, se retoma en el paso 4 una sola vez para aplicar de forma incremental cualquier versión posterior a `snapshotVersion` y luego continúa en el paso 9. Si en esa segunda pasada se vuelve a detectar discontinuidad, se registra el error y termina. Si la sincronizacion completa (C01) falla, termina (C01 registra el error y C03 reintentará).<br>**6.1, `catedra:sync:changes:{v}` no existe (fuera de la ventana retenida) o no puede interpretarse:** se trata como discontinuidad, igual que 5.2.<br>**6.2, Un ID afectado no está en su Hash de Redis o referencia una entidad inexistente:** estado no verificable, se trata como discontinuidad, igual que 5.2.<br>**6.3, Redis falla durante la lectura (timeout o corte):** igual que 4.1, retomando en el paso 6.<br>**7.1, Falla la persistencia:** se revierte la unidad de trabajo de esa versión (la copia y la versión quedan en la última versión aplicada correctamente), se registra el error y se aplica la política de reintentos de 4.1, retomando en el paso 6. |
| **Postcondición** | **- Éxito:** la copia local refleja el estado vigente de todas las versiones aplicadas, la versión local es la última pendiente aplicada (`currentVersion` leída en el paso 4, o `snapshotVersion` si se ejecutó la sincronizacion completa(C01)) y el `eventId` queda registrado como procesado.<br>**- Fracaso:** la versión local queda en la última versión aplicada de forma completa (nunca avanza sin sus cambios aplicados) y el error queda registrado.<br>**- Reprocesar** el mismo aviso no cambia el resultado final (por `eventId` y por comparación de versiones). |

| **NOMBRE** | C03 — Verificar la versión del catálogo periódicamente |
| --- | --- |
| **Actor principal** | Tiempo (arranque del servicio e intervalo periódico) |
| **Actor secundario** | Servicio de la cátedra (Redis; REST a través de sincronizacion completa (C01) cuando hace falta reconstruir) |
| **Descripción** | Compara la versión local del catálogo con la vigente en Redis, al arrancar y cada cierto intervalo, para detectar avisos de Kafka perdidos o atrasos. Recupera el atraso de forma incremental y, si no es posible, reconstruyendo con sincronizacion completa (C01). Es la red de seguridad de la sincronizacion incremental (C02). |
| **Alcance** | Servicio de catálogo y sincronización |
| **Precondición** | - Autenticacion de cuenta tecnica (X01) completada (credenciales de Redis disponibles).<br>- El intervalo de verificación está configurado. |
| **Flujo** | **1-** Tiempo dispara la verificación: al arrancar el servicio (después de la autenticacion de la cuenta tecnica) y luego a intervalos periódicos.<br>**2-** El servicio comprueba que no haya otra sincronización en curso.<br>**3-** Lee en Redis la metadata del catálogo (`currentVersion` y `oldestAvailableVersion`).<br>**4-** Compara con la versión local y detecta un atraso: la versión local es menor que `currentVersion` y no es menor que `oldestAvailableVersion`.<br>**5-** Aplica de forma incremental las versiones pendientes, con el mismo procedimiento que los pasos 6 a 8 de la sincronizacion incremental (C02), registrando esa aplicación como una sincronización de tipo `INCREMENTAL`.<br>**6-** Registra el resultado de la verificación (versión local, `currentVersion`, fecha y resultado). |
| **Flujo alternativo** | **2.1, Ya hay otra sincronización en curso:** se omite esta verificación y termina. La siguiente ejecución periódica la repetirá.<br>**3.1, Redis no está disponible (timeout o corte de conexión):** se reintenta con espera creciente y un máximo de intentos. Si se agotan, se registra el error, la versión local no cambia y termina hasta el siguiente ciclo.<br>**3.2, Redis rechaza las credenciales:** se ejecuta la autenticacion de la cuenta tecnica para obtener la configuración vigente y se retoma en el paso 3, una sola vez. Si persiste, se registra el error y termina como en 3.1.<br>**4.1, La versión local es igual a `currentVersion`:** el catálogo está al día; se registra la verificación y termina.<br>**4.2, No hay versión local, es menor que `oldestAvailableVersion` o es mayor que `currentVersion` (discontinuidad o estado no verificable):** se ejecuta una sincronizacion completa (C01). Si termina con éxito, se retoma en el paso 3 una sola vez para aplicar de forma incremental cualquier versión publicada después de `snapshotVersion`. Si la sincronizacion completa (C01) falla, termina (C01 registra el error) y se reintentará en el siguiente ciclo. Si en esa segunda pasada se vuelve a detectar discontinuidad, se registra el error y termina hasta el siguiente ciclo.<br>**5.1, Al aplicar una versión, `changes:{v}` no existe o no puede interpretarse, o un ID afectado no está en su Hash de Redis:** estado no verificable, se trata como discontinuidad, igual que 4.2.<br>**5.2, Redis falla durante la lectura o falla la persistencia:** se revierte la unidad de trabajo de esa versión (la versión local queda en la última aplicada), se reintenta con la política de 3.1 y, agotados los intentos, se registra el error y termina hasta el siguiente ciclo. |
| **Postcondición** | **- Éxito:** la versión local coincide con la `currentVersion` leída en Redis y queda registrado el resultado de la verificación.<br>**- Fracaso:** la versión local queda en la última versión aplicada de forma completa y se reintentará en el siguiente ciclo. |

| **NOMBRE** | C04 — Listar categorías |

| **Actor secundario** | Ninguno |

Es un endpoint expresamente público. Solo lee la copia local y nunca consulta a la cátedra. Si la solicitud incluye un JWT, sea válido o inválido, el servicio no lo valida ni lo usa: el caso es público y no depende de la identidad del usuario. |
| **Alcance** | Servicio de catálogo y sincronización |
| **Precondición** | - Ninguna. Es un endpoint expresamente público: no requiere sesión. |
| **Flujo** | **1-** La app solicita las categorías al servicio de catálogo.<br>**2-** El servicio consulta la copia local y obtiene todas las categorías, habilitadas y deshabilitadas.<br>**3-** Devuelve la lista ordenada por nombre, con `id`, `name`, `description` y `enabled` de cada categoría.|

| **Postcondición** | - No se modifica ningún dato.<br>- La app dispone de todas las categorías con su estado (`enabled`) y decide cómo mostrarlas.<br>- La lectura ve siempre una copia consistente (anterior o posterior a una sincronización, nunca parcial). |

| **NOMBRE** | C05 — Buscar profesionales |
| --- | --- |
| **Actor principal** | Aplicación KMP |
| **Actor secundario** | Ninguno |
| **Descripción** | Devuelve a la app, sin requerir sesión, una página de profesionales de la copia local que cumplen los filtros indicados (categoría, nombre, estado habilitado y disponibilidad semanal). Es un endpoint expresamente público. Cada profesional viaja con su estado, su categoría y sus horarios semanales para que la app decida cómo presentarlos. Los profesionales de una categoría deshabilitada también se devuelven, con el estado de su categoría. Aquí "disponibilidad" significa que el profesional atiende en un día o franja según sus horarios semanales; los turnos libres de una fecha concreta se consultan en el servicio de turnos (T03). Solo lee la copia local y nunca consulta a la cátedra ni al servicio de turnos. Si la solicitud incluye un JWT, sea válido o inválido, el servicio no lo valida ni lo usa: el caso es público y no depende de la identidad del usuario. |
| **Alcance** | Servicio de catálogo y sincronización |
| **Precondición** | - Ninguna. Es un endpoint expresamente público: no requiere sesión. |
| **Flujo** | **1-** La app envía la búsqueda al servicio de catálogo. Todos los filtros son opcionales y se combinan entre sí: `categoryId`, `name`, `enabled`, `dayOfWeek` (uno o varios días) y una franja horaria (`from` y/o `to`). Incluye la paginación (`page` y `size`).<br>**2-** El servicio valida los parámetros recibidos (valores permitidos, franja coherente y límites de paginación).<br>**3-** Consulta la copia local y selecciona los profesionales que cumplen todos los filtros indicados: por `categoryId`, los de esa categoría; por `name`, los que coinciden parcialmente, sin distinguir mayúsculas ni tildes, con el nombre, el apellido o ambos; por `enabled`, los que tienen ese estado; por disponibilidad, los que tienen al menos un horario semanal habilitado en alguno de los `dayOfWeek` indicados que se solapa con la franja indicada. Sin filtros se consideran todos los profesionales, habilitados o no.<br>**4-** Ordena los resultados por apellido, nombre e `id` y toma la página solicitada.<br>**5-** Devuelve la página con el total de resultados, la página y el tamaño. Cada profesional incluye `id`, `firstName`, `lastName`, `enabled`, su categoría (`id`, `name`, `enabled`) y sus horarios semanales (`dayOfWeek`, `startTime`, `endTime`, `slotDurationMinutes`, `enabled`). |
| **Flujo alternativo** | **1.1, La solicitud incluye un JWT, sea valido o inválido:** Se ignora y la solicitud se trata como anónima, porque el endpoint es público.<br>**2.1, Algún parámetro es inválido (`dayOfWeek` fuera de `MONDAY` a `SUNDAY`, hora con formato inválido, `from` no anterior a `to`, `categoryId` no numérico, `page` negativa o `size` fuera del rango permitido):** responde `400` con un código funcional y el detalle de los campos inválidos, sin consultar la copia local; termina.<br>**3.1, La copia local todavía no fue inicializada (no hay versión local aplicada):** responde que aún no está inicializado (`503` con un código funcional), sin consultar a la cátedra, y termina.<br>**3.2, Ningún profesional cumple los filtros (incluye un `categoryId` inexistente):** se devuelve una página vacía (`200`) con total 0.<br>**3.3, Falla el acceso a la base local:** se registra el error y se responde un error del servidor (`500` o `503`) sin exponer detalles internos; termina.<br>**4.1, La página solicitada está más allá de la última:** se devuelve una página vacía (`200`) con el total real de resultados. |
| **Postcondición** | - No se modifica ningún dato.<br>- La app dispone de una página de profesionales con su estado, su categoría y sus horarios semanales, y decide cómo mostrarlos.<br>- La lectura ve siempre una copia consistente (anterior o posterior a una sincronización, nunca parcial). |

| **Postcondición** | - No se modifica ningún dato.<br>- Turnos dispone de los datos vigentes del profesional para continuar con T03 o T04.<br>- La lectura ve siempre una copia consistente (anterior o posterior a una sincronización, nunca parcial). |

| **NOMBRE** | C07 — Consultar estado de sincronización |
| --- | --- |
| **Actor principal** | Cliente autenticado con rol ADMINISTRADOR (la app en nombre de un administrador, o una herramienta de administración/evidencia como Postman o Swagger) |
| **Actor secundario** | Ninguno |
| **Descripción** | Devuelve el estado actual de la sincronización del catálogo: si la copia local está inicializada, la versión local, la `currentVersion` conocida en Redis, el tipo (`FULL` o `INCREMENTAL`), el resultado y la fecha de la última sincronización que aplicó cambios (C01 o C02/C03), y si hay un atraso o un error registrado. Sirve para vigilar la salud de la integración y como evidencia del comportamiento del servicio, y queda restringido a quien tiene rol ADMINISTRADOR. No modifica nada. |
| **Alcance** | Servicio de catálogo y sincronización |
| **Precondición** | - Quien consulta tiene un JWT vigente con rol ADMINISTRADOR. |
| **Flujo** | **1-** El cliente solicita el estado de sincronización al servicio de catálogo, con el JWT vigente.<br>**2-** El servicio valida el JWT (firma, vigencia y que incluya el rol ADMINISTRADOR).<br>**3-** Recupera el último resultado de sincronización que aplicó cambios (de C01 o C02/C03) y la versión local.<br>**4-** Intenta leer en Redis la `currentVersion` vigente, para informar si hay atraso.<br>**5-** Devuelve el estado: `initialized`, `localVersion`, `lastSyncAt`, `lastSyncType` (`FULL` o `INCREMENTAL`), `lastSyncResult` (éxito o error, con el tipo de error si corresponde) y, si pudo leer Redis, `remoteVersion` y si hay atraso (`localVersion` menor que `remoteVersion`). |
| **Flujo alternativo** | **2.1, El JWT falta, es inválido o está vencido:** responde `401` sin datos y termina.<br>**2.2, El JWT es válido pero no tiene el rol ADMINISTRADOR:** responde `403` sin datos y termina.<br>**3.1, Todavía no se aplicó ninguna sincronización:** se informa `initialized: false` y el resto de los campos vacíos.<br>**4.1, Redis no está disponible:** se informa igual el estado local (paso 3), sin `remoteVersion` ni el indicador de atraso, y se aclara que no pudo verificarse contra la cátedra. No se reintenta ni se ejecuta X01, porque es una consulta de solo lectura y no debe demorar la respuesta. |
| **Postcondición** | - No se modifica ningún dato.<br>- Quien consulta conoce el estado de la sincronización al momento de la solicitud. |
